================================================================================
Core math baseline — 2026-05-10
================================================================================

Reference run for the core-math-optimization plan (docs/plans/core-math-
optimization.md). Every phase-1+ change measures against these numbers.

Hardware / toolchain:
  - Apple Silicon (arm64), 12-core
  - macOS 26.3.1, Darwin 25.3.0
  - Apple clang 16.0.0 (clang-1600.0.26.6)
  - Build: cmake --preset benchmark (release flags: -O3 -funroll-loops
    -mtune=native), Google Benchmark 1.8.3
  - Source commit: a064505e91b374a355bf714eda5f696e7d266c48 (branch master)
  - --benchmark_min_time=0.1s; spatial-index benchmarks excluded with
    --benchmark_filter='-bm_intersect<|-bm_shadow|-bm_build<' (they are
    container-level benchmarks; out of scope for this baseline)

Re-baseline trigger: anything in Phase 1 (per docs/plans/core-math-
optimization.md) plus a compiler bump in CI.

Reading notes:
  - Time / CPU columns are nanoseconds per call.
  - Iterations is the count Google Benchmark settled on for ~0.1s runtime;
    higher iterations means a faster per-call cost.
  - Items/sec where present is from state.SetItemsProcessed (batched ops).
  - Single-op microbenchmarks wrap every input in DoNotOptimize() so
    the compiler can't constant-fold; an earlier draft of the run showed
    ~0.3 ns for every microbenchmark because of constant folding —
    that's the failure mode to look out for if a future change makes
    a benchmark look implausibly fast.

Observations worth flagging at baseline:
  - random_threaded shows real-time scaling linearly with thread count
    (6.5/3.2/1.7/1.0) but CPU-time-per-call flat (6.4/6.4/6.9/7.8) — so
    on this Darwin libc, std::rand isn't lock-contended. Glibc would
    contend hard; the PRNG replacement still matters for portability +
    statistical quality.
  - bm_quartic_sorted_result is ~2.5x slower than bm_quartic_solve_into
    (160 ns vs 72 ns) — the per-call std::vector allocation in
    sortedResult() is the largest single chunk of Phase 1 opportunity.
  - bm_inverted4 is ~25 ns / ~27 ns at float / double — that's the
    cofactor-expansion baseline; block-inverse target is <10 ns.
  - bm_matmul<Matrix4> is ~5.5 ns regardless of float vs double; the
    SIMD target is <2 ns for float, <3 ns for double.
