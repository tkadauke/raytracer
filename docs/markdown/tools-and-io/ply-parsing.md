# PLY parsing

The codebase ships one geometry import format: **PLY** —
sometimes "Polygon File Format," sometimes "Stanford Triangle
Format," after the Stanford computer graphics laboratory that
introduced it in the early 1990s. PLY's design goal was *to
store any kind of polygon-mesh data without committing to a
specific application's needs*, and the result is a format that
ships every vertex's position plus arbitrary additional
per-vertex and per-face attributes.

PLY is also the *only* format the codebase reads from
untrusted input. Every other input is either generated
internally (procedural primitives, scene-graph JSON written by
the codebase itself) or trusted (test fixtures, hand-edited
scene files). PLY files come from outside — the Stanford bunny
mesh, downloaded scans, a third-party model — and the parser
must therefore be defensive about malformed input. This
chapter covers both the format and the defenses.

By the end of this chapter you should know:

- the PLY format's two encodings (ASCII and binary) and the
  shared header,
- the codebase's parser structure (header pass, then data
  pass, with element / property descriptors driving the
  data-side reads),
- the threat model for PLY input and the parsing-error
  contract,
- the LibFuzzer harness that pins the parser's robustness.

## <a id="the-format"></a>The format
A PLY file always starts with a plaintext header. Even binary
PLYs have an ASCII header — only the data section is binary. A
typical header for a triangle mesh:

```
ply
format ascii 1.0
comment generated by ...
element vertex 1745
property float x
property float y
property float z
property float nx
property float ny
property float nz
element face 3490
property list uchar int vertex_indices
end_header
```

Reading the header line by line:

- `ply` is the file's magic number — every [PLY](../appendix/a-glossary.md#p) file starts with
  this exact line.
- `format ascii 1.0` declares the encoding. The alternatives
  are `format binary_little_endian 1.0` and
  `format binary_big_endian 1.0` for the two binary variants.
- `comment ...` is metadata — ignored by parsers, used for
  attribution.
- `element <name> <count>` declares one section of records,
  with the given count of records to follow.
- `property <type> <name>` declares one field per record,
  inside the most recent `element`. Property types are scalar
  (`float`, `int`, `uchar`, etc.) or list (`list <count_type>
  <element_type>`).
- `end_header` ends the header and starts the data section.

After the header, the data section has $N$ records of the first
element, then $N$ records of the second, and so on. In ASCII
mode each record is one line of whitespace-separated values; in
binary mode each record is a sequence of bytes packed in the
declared order.

A typical mesh declares two elements: `vertex` (with `x`, `y`,
`z` plus optional normals and UVs) and `face` (with a single
list property `vertex_indices` — the variable-length list of
vertex indices that make up each polygon).

The format is **flexible**: a parser doesn't know in advance
what properties any given file declares. The parser has to
read the header to learn what's in the data section, then read
the data according to the header's property declarations.

## <a id="the-codebase-s-parser"></a>The codebase's parser
[`PlyFile`](../../../src/core/formats/ply/PlyFile.cpp) is the
top-level parser, with helpers in
[`PlyElement.cpp`](../../../src/core/formats/ply/PlyElement.cpp)
and
[`PlyProperty.cpp`](../../../src/core/formats/ply/PlyProperty.cpp).
The structure is two passes:

1. **Header pass.** Read lines until `end_header`. Build a
   list of `PlyElement` descriptors, each carrying an ordered
   list of `PlyProperty` descriptors. After the header pass,
   the parser knows what's coming in the data section — which
   elements, how many records each, what fields per record.
2. **Data pass.** For each element in declaration order, for
   each record, for each property: read the value from the
   stream and either store it into the output `Mesh` (for
   recognized properties like `x`, `y`, `z`, `vertex_indices`)
   or skip it (for unrecognized properties).

The recognized-properties handling is what bridges PLY to the
codebase's
[`Mesh`](../../../include/core/geometry/Mesh.h) type. PLY's
`vertex` element with `x`/`y`/`z` properties becomes a vector
of `Mesh::Vertex` records with the position field populated.
PLY's `face` element with `vertex_indices` becomes a vector of
`Mesh::Face` records. PLY's normal properties (`nx`, `ny`, `nz`)
and texture properties (`s`, `t` or `u`, `v`) populate the
respective `Mesh::Vertex` fields.

Properties the parser doesn't recognize get *silently skipped*
— their bytes are read off the stream and discarded. This is
the right default for the format's open-ended philosophy:
some PLY files carry application-specific attributes the
codebase doesn't have a use for, but skipping them lets the
parser still extract the geometry.

## <a id="the-threat-model"></a>The threat model
Why does the threat model matter? Because PLY is the only
unsafe input the codebase processes. The other inputs — JSON
scene files, command-line arguments, internally generated data
— are all either trusted or have well-defined boundaries that
the renderer's logic enforces. A malformed PLY, by contrast,
can come from anywhere: a third-party model from the internet,
a partially-downloaded asset, an attacker-controlled file
landed in the test fixtures.

Three classes of malformed PLY are worth defending against:

**Header tampering.** A PLY header that lies about how many
elements follow, or declares more properties than the data
section actually contains. A naive parser that trusts the
declared count blindly reads past the end of the data,
crashing on EOF, or — worse — reads into adjacent memory if
the input is in-memory and the parser uses pointer arithmetic.

**Element-count overflow.** A header that declares
$2^{31}$ vertices. A parser that pre-allocates one
`Mesh::Vertex` per declared count tries to allocate ~50 GB and
crashes. The parser needs to bound element counts to a
sensible maximum or stream-process records without
preallocating.

**List-length overflow.** A `face` record whose
`list uchar int vertex_indices` declares 255 indices but the
data section only carries 3. A naive parser reads 255 ints
past the actual data, drifting into the next element's data.

The contract the codebase enforces is: **any malformed input
throws `PlyParseError` (or another `Exception`), never
crashes the process**. This is the invariant the LibFuzzer
harness checks — see [The fuzzer harness](#the-fuzzer-harness).

## <a id="the-fuzzer-harness"></a>The fuzzer harness
[`fuzz/fuzz_ply.cpp`](../../../fuzz/) is a LibFuzzer harness
that feeds randomly-generated and randomly-mutated byte
streams into the PLY parser. LibFuzzer is part of the LLVM
toolchain; it generates input bytes, hands them to a
target function, watches for crashes, and uses *coverage
feedback* (instrumentation that tracks which code paths the
input exercised) to evolve inputs that explore deeper into
the parser.

The harness is short:

```cpp
// fuzz/fuzz_ply.cpp (sketch)
extern "C" int LLVMFuzzerTestOneInput(const uint8_t* data, size_t size) {
  std::stringstream ss;
  ss.write(reinterpret_cast<const char*>(data), size);
  Mesh mesh;
  try {
    PlyFile parser(ss, mesh);
  } catch (const Exception&) {
    // expected: parser threw on malformed input
  }
  return 0;
}
```

Two cases survive: (a) the input is well-formed PLY, the
parser succeeds, the harness returns. (b) the input is
malformed, the parser throws `PlyParseError` or another
`Exception`, the catch swallows it, the harness returns. The
*third* case — the parser crashes (segfault, abort, hang) —
is the case the fuzzer is hunting. Any crash is a bug in the
parser.

The harness runs continuously in CI on each PR, and on a
nightly dedicated fuzz job that runs for a longer time. New
crash-inducing inputs go into the regression corpus and the
parser gets fixed; the regression corpus replays on every
subsequent run.

Specific malformed-input shapes the parser handles correctly
include properties declared before any element, missing or
negative element counts, positive-count full reads without
properties, truncated scalar data, and negative list counts.
All of these throw `PlyParseError` rather than producing
undefined behavior.

## <a id="what-the-parser-doesn-t-accept"></a>What the parser doesn't accept
By design, the parser accepts the *common* PLY profile and
rejects unusual variants. Specifically:

- **No "pure-binary" PLY** (a hypothetical PLY that's all
  bytes from the first one). The header is mandatory ASCII;
  the parser refuses input without a recognizable text
  header.
- **No 64-bit element counts.** The parser caps element
  counts at the platform's `int` range — billions of elements
  is enough for any practical mesh, and capping protects
  against the overflow case from [The threat model](#the-threat-model).
- **No commented data.** Comments are header-only; data lines
  are parsed strictly. A `# this is a comment` in the data
  section is a parse error.
- **No backwards compatibility with broken older PLY
  variants.** A few early PLY producers wrote files that
  violated even the loose 1990s spec — the parser doesn't
  attempt to recover from those.

The acceptance set covers every PLY file the codebase has
encountered in practice (Stanford bunny, dragon, Stanford
photogrammetry datasets, and the procedurally-generated PLYs
the test suite writes for fixtures). Files outside that set
either get rejected with a clear `PlyParseError` (the safe
behavior) or, in extremely rare cases, get accepted with
imperfect interpretation (the parser's flexibility around
unrecognized properties).

## <a id="what-this-chapter-does-not-cover"></a>What this chapter does *not* cover
Additional file-format topics are queued under
`docs/topics-backlog.md`:

- **OBJ.** The Wavefront OBJ format. Older and less
  type-rich than PLY, but more widely supported by
  third-party tools. Not yet implemented.
- **STL.** The stereo-lithography format used by 3D printers.
  Triangle-only, no UVs or normals. Trivial to implement.
- **LDraw.** The LEGO part-library format. The codebase now has
  a command-record parser for `.dat` and `.ldr` files plus inline
  type 3/4 polygon conversion to renderable mesh primitives. Type-1
  referenced files resolve through a file resolver and are instanced
  with LDraw affine transforms and color inheritance. MPD files are
  split into `0 FILE` / `0 NOFILE` blocks so type-1 references can
  resolve embedded submodels before falling back to external library
  roots. The shared `world::SceneImporter` surface is the next layer
  above these format-specific pieces: importers report supported
  extensions and option schemas, return an owned scene or group root,
  attach source metadata, and distinguish warning diagnostics from
  import-blocking errors.
- **glTF.** The modern web-graphics interchange format. JSON
  + binary blob, supports materials, animations, multiple
  meshes per file. The richest format, the most work to
  implement.

These are reasonable additions, but PLY remains the established
format for academic-graphics meshes (which is what most of the
test fixtures use), so it gets pride of place.

## <a id="exercises"></a>Exercises
1. Predict what happens when a PLY file declares
   `element vertex 100` but has only 50 vertex records in the
   data section. What error does the parser throw? At what
   point in the parse?
2. Compare ASCII PLY parsing cost to binary PLY parsing
   cost for a 1-million-vertex mesh. Estimate both: ASCII
   needs to lex each line and convert text to floats; binary
   needs only to interpret the bytes.
3. Write a sketch PLY file (header + data section) for a
   tetrahedron with 4 vertices and 4 triangular faces.
   Hand-trace it through the parser: what would the parser
   produce, and at what step does each property get read?
4. The codebase's parser silently skips unrecognized
   properties. What's the failure mode if a file declares an
   element with one recognized property and one unrecognized
   property of variable size? What invariant does the parser
   need to maintain to handle this?
